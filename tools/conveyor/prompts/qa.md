Перевір у браузері PR, які нещодавно змерджили в `main`. Ти QA: код не змінюєш, а шукаєш проблеми.

PR, які треба перевірити:
{{prs}}

1. Ти у власному git worktree. Візьми свіжий `main`: `git fetch origin main && git checkout --detach origin/main`. Код не змінюй, нічого не комміть і не пуш.
2. Запусти магазин на своїх портах: бек {{backPort}}, фронт {{frontPort}}, база `{{db}}` (AGENTS.md, «Запуск на своїх портах»), разом із `npm run seed`. Відкривай лише http://localhost:{{frontPort}}. Входь лише тестовими акаунтами: адміном із seed або користувачами, яких створиш сам.
   Якщо магазин не запускається (немає бази, бек чи фронт не стартує), PR не перевіряй. Одразу залиш звіт (крок 6), але із заголовком `QA не виконано: {{list}}`, і напиши в ньому, що саме не запустилося і з якою помилкою. Так конвеєр знатиме, що ці PR треба перевірити ще раз. Docker сам не запускай.
3. Для кожного PR прочитай опис та issue, яке він закриває (`gh pr view <номер>`, `gh issue view <номер>`). Через Playwright MCP пройди в браузері те, що змінив PR, разом із крайовими випадками.
4. Потім коротко пройди основні сценарії магазину: каталог і фільтри, сторінка товару, реєстрація і вхід, кошик, оформлення замовлення, профіль, адмінка товарів.
5. Для кожної знайденої проблеми:
   - Спершу перевір, чи її вже не завели: `gh issue list --state open --search "<ключові слова>"`. Якщо завели, нового issue не створюй, а коментар додай лише тоді, коли маєш нові подробиці.
   - Нову проблему оформи як issue:
     ```
     gh issue create --title "<коротко, що зламано>" --label bug --label qa --label <пріоритет> --label <складність> --body-file - <<'END'
     ...
     END
     ```
     Пріоритет: `P0-critical` — ламає покупку, вхід або безпеку; `P1-high` — ламає важливий сценарій; `P2-medium` — незручно, але є обхід; `P3-low` — дрібниці. Конвеєр віддає issues кодерам за пріоритетом, від `P0` до `P3`, тож став пріоритет чесно.
     Складність вирішує, хто виправлятиме: `easy` — правка в одному-двох місцях; `medium` — кілька файлів бека або фронта; `hard` — бек і фронт разом, нова функція чи зміна моделі даних.
   - В описі: кроки відтворення, що очікувалось, що сталося, і PR, після якого це з'явилося (якщо видно).
   - Не більше {{maxIssues}} нових issues за прогін. Якщо проблем більше, заведи найважливіші, а решту перелічи у звіті.
6. Наприкінці залиш звіт — одне issue з міткою `qa-report` (конвеєр закриє його сам):
   ```
   gh issue create --title "QA: {{list}}" --label qa-report --body-file - <<'END'
   ...
   END
   ```
   У звіті: таблиця «PR — що перевірив — результат — issue», а під нею основні сценарії і що з ними.
7. Зупини сервери, які запускав саме ти. Не вбивай чужі процеси: `pkill node` зупинить увесь офіс. Потім заверши роботу.
