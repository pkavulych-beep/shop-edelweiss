# Конвеєр

Скрипт-диспетчер, який без участі людини веде задачі через Agent Office: issue → код → CI → рев'ю → мердж → QA. Сам він не витрачає токенів моделей: лише читає GitHub і стан офісу, а потім наймає агентів і мерджить.

## Як рухається задача

```
issue у черзі ──► кодер за складністю (hard → Opus, medium → Codex) ──► PR
PR відстає від main або CI ще не запускався ──► підтягнути main у гілку ──► CI
конфлікт або червоний CI ──► повернути автору (або найняти фіксера)
CI зелений, вердикту нема ──► рев'юер (по одному PR за раз) ──► коментар із вердиктом
вердикт changes ──► повернути на доопрацювання ──► рев'ю знову (максимум maxReviewRounds кіл, останнє доопрацювання робить escalateTo)
вердикт approve ──► мердж, якщо PR не чіпає захищені файли й не завеликий (один за крок: решта спершу підтягує main), інакше — після мітки merge-ok від тебе
кожні qa.everyMerges мерджів коду ──► QA-агент у браузері ──► issues з багами і звіт
```

У черзі — відкриті issues з міткою `agent`, а також твої issues з пріоритетом `P0`–`P3` (`autoPriorities`). Мітка `manual` не пускає issue в чергу. Першим іде вищий пріоритет, а за однакового — старіше issue. Рядок «Залежить від #12, #13» в описі issue тримає його в черзі, доки ті issues не закриються: так великі задачі робляться по кроках.

## Кодери

Пріоритет каже, що робити першим, а мітка складності — хто це робитиме:

| Кодер | Бере складність | Порти (бек, фронт) і база |
|---|---|---|
| Opus | `hard` | 7777, 3000, `Edelweiss` |
| Codex (`gpt-5.6-terra`) | `medium` | 7778, 3001, `Edelweiss_codex` |
| Zen: OpenCode з безкоштовною моделлю `opencode/big-pickle` | `easy`, `medium` | 7780, 3003, `Edelweiss_zen` |
| DeepSeek: OpenCode з безкоштовною моделлю `opencode/deepseek-v4.1-flash-free` | `easy`, `medium` | 7781, 3005, `Edelweiss_deepseek` |
| MiMo: OpenCode з безкоштовною моделлю `opencode/mimo-v2.6-flash-free` | `easy`, `medium` | 7783, 3007, `Edelweiss_mimo` |
| Nemotron: OpenCode з безкоштовною моделлю `opencode/nemotron-3.5-super-vl-free` | `easy`, `medium` | 7784, 3008, `Edelweiss_nemotron` |
| GLM: OpenCode з безкоштовною моделлю `opencode/glm-5.3-flash-free` (у запасі) | `easy` | 7782, 3006, `Edelweiss_glm` |

Якщо агент відкрив PR без рядка `Closes #N` (буває, що модель пише його українською), конвеєр знаходить PR за гілкою агента й дописує цей рядок сам. Інакше він вирішив би, що PR немає, і віддав би задачу ще одному кодеру.

Issue без мітки складності вважається `medium` (`defaultDifficulty`). Кодери працюють одночасно, кожен над однією задачею, на своїх портах і зі своєю базою. Вільні кодери беруть задачі в тому порядку, в якому стоять у `config.json`: задачу `easy` беруть Zen, DeepSeek, MiMo і Nemotron, а GLM — лише коли всі вони зайняті. Задачу `medium` бере той із Codex, Zen, DeepSeek, MiMo і Nemotron, хто вільний. Безкоштовних моделей кілька, бо денний ліміт у кожної свій і закінчується за годину-дві роботи: що більше моделей, то довше задачі не стоять. Доопрацювання PR бере той кодер, який його написав: конвеєр пам'ятає, хто робив issue, тож безкоштовні кодери не плутаються, хоч усі працюють через OpenCode. Якщо модель автора на паузі (ліміт чи модель недоступна), доопрацювання не чекає на неї: його робить новий агент іншого вільного кодера, який бере ту саму складність.

Рев'ю PR робить Opus, а PR задач `easy` — Sonnet (`reviewerFor`): так рев'ю простих змін витрачає менше ліміту Claude. Невеликий PR в авторизації чи оплаті завжди рев'юїть Opus, бо його схвалення може змерджити PR без тебе (див. нижче).

Ліміт підписки в кожного провайдера свій. Конвеєр помічає повідомлення про ліміт у терміналі агента, навіть коли агент ще вважається зайнятим: Codex після ліміту зависає на питанні про дешевшу модель. Далі він не наймає агентів цього провайдера, доки ліміт не скинеться: час береться з повідомлення («try again at Nov 3rd…», «resets 3am»), а якщо його там немає, — `limitPauseMinutes`. Повідомлення, чий час скидання вже минув, паузи не ставить: воно лишається на екрані агента й після скидання, а агента, який на ньому зупинився, конвеєр один раз просить продовжити. Claude Code пише тільки годину, коли до скидання менше доби, тому для ліміту сесії (5 годин) година, що минула менш ніж 18 годин тому, означає скидання, яке вже відбулося, а для тижневого — завтрашнє. Якщо чекати недовго, той самий агент потім продовжить задачу. Якщо довше за `releaseAfterHours`, агент іде додому, а задача повертається в чергу без штрафної спроби. Решта працює далі: наприклад, коли Codex вичерпав місячний ліміт, його задачі чекають, а Opus і рев'юер працюють.

Безкоштовні моделі OpenCode мають щоденний ліміт, окремий для кожної моделі (скидається опівночі за UTC). Коли він закінчується, OpenCode пише «Free usage exceeded … [retrying in 2h 36m]» і сам повторить запит, щойно ліміт скинеться. Тому конвеєр ставить на паузу лише цю модель, наприклад Zen, а не весь OpenCode: DeepSeek працює далі. Агентові він нічого не друкує, бо відкрите вікно «Free limit reached» сприйняло б Enter як «subscribe». Якщо до скидання більше години (`releaseAfterHours.opencode`), агент іде додому, а задачу бере інший вільний кодер.

Безкоштовні моделі OpenCode буває й зникають: модель перестає відповідати («Upstream request failed: Model is unavailable») або її прибирають зі списку («Model not found»). Агент тоді стоїть на помилці так, ніби чекає відповіді, але відповідь не допоможе. Тому конвеєр, побачивши таке в терміналі, не кличе людину, а ставить модель на паузу на `modelDownHours` годин, відправляє агента додому й повертає задачу в чергу без штрафної спроби: її бере інший вільний кодер. Модель, яка зникла назовсім, варто замінити в `config.json`.

Codex без нагляду налаштований у `.codex/config.toml`: пісочниця з доступом до мережі, а дії поза нею схвалює автоматичний рев'юер Codex, а не людина. OpenCode — в `opencode.json`: пісочниці в нього немає, тож він може все, крім небезпечних команд (force-push, пуш у `main`, `git reset --hard`, `pkill`, `sudo`, `rm -rf` від кореня чи домашньої папки), не питає людину і не виходить за межі свого worktree. Ключ OpenCode Zen лежить локально в OpenCode (`opencode auth login`). Браузер для обох кодерів — Playwright MCP з `--isolated`, щоб кілька агентів могли відкрити його одночасно. Для Claude це налаштовується один раз:

```bash
claude mcp remove playwright -s user
claude mcp add --scope user playwright -- npx @playwright/mcp@latest --isolated
```

Усе, що конвеєр не може зрушити сам, отримує мітку `needs-human` і коментар із причиною. Коли знімаєш мітку, задача повертається в конвеєр, а лічильники кіл і спроб для неї починаються з нуля.

Буває, що агент зупинився, а результату немає: після доопрацювання PR не змінився або рев'юер не залишив вердикту. Його роботу могли перервати перезапуск офісу чи збій агента, тож конвеєр спершу дає ще одну спробу і не рахує її колом. Доопрацювання спершу дістається автору PR: його знаходять за PR, а якщо офіс PR не знає — за гілкою. Друга спроба дістається новому агенту, бо автор міг застрягти там, куди не доходить надрукований текст (наприклад, у діалозі Claude Code). `needs-human` з'являється, лише коли й друга спроба нічого не дала.

Рев'ю має `maxReviewRounds` кіл. Перші доопрацювання робить автор PR, а останнє — `escalateTo` (Opus) як новий агент у гілці PR: безкоштовні моделі добре дають раду простим зауваженням, але буксують на тонких, як-от гонка в роутері чи розрахунок грошей. `needs-human` через рев'ю з'являється, лише коли не впорався й він.

PR, який рев'ю схвалило, але конвеєр не мерджить сам (завеликий чи змінює захищені файли), чекає на тебе з `needs-human`. Подивися його і, якщо все гаразд, постав мітку `merge-ok` (можна й з телефона): конвеєр сам підтягне main, дочекається CI і змерджить. Мітка знімає лише те, що тримало схвалений PR (розмір, захищені файли), і діє, поки рев'ю схвалює його поточні коміти. Якщо після мітки в PR з'явився конфлікт (змерджили інший PR) чи червоний CI, конвеєр повертає PR кодеру, віддає нові коміти на рев'ю і, коли рев'ю схвалить їх, змерджить без повторної мітки. Решта причин `needs-human` (наприклад, рев'ю не пройдено після всіх кіл) чекає на тебе, як і без мітки, а про ту саму причину конвеєр питає один раз. Тести (`*.spec.ts`, `test/`) до розміру PR не рахуються.

Невеликий PR, який із захищених файлів змінює лише код авторизації чи оплати (`merge.doubleReview`: `src/auth/`, `src/payment/`, до 300 рядків без тестів), до тебе не йде. Після першого схвалення конвеєр наймає друге, незалежне рев'ю Opus, і коли його поточні коміти схвалили обидва, мерджить сам. Нові коміти після схвалення (крім підтягнутого main) потребують обох схвалень знову. Якщо друге рев'ю двічі не залишило вердикту, PR чекає на тебе. Більший PR в авторизації чи оплаті, а також зміни в `.github/`, конвеєрі, AGENTS.md та інших захищених файлах і далі йдуть тобі.

## QA

Коли після останнього QA змерджено `qa.everyMerges` PR, які змінили код магазину (`qa.paths`), конвеєр наймає QA-агента. QA запускає магазин на своїх портах (`qa.ports`), тож працює паралельно з кодерами. Базу він заповнює `npm run seed`, а якщо в беку є `seed:demo`, то й демо-товарами: так QA не витрачає токени на те, щоб створювати товари вручну.

За один прогін QA перевіряє не більше `qa.everyMerges` PR, найстаріші першими, а решта переходить у наступний прогін. Менше мерджів чекають на повний набір, бо прогін коштує майже стільки ж, скільки б PR він не перевіряв. Лише коли найстаріший неперевірений мердж чекає `qa.maxWaitHours` годин, QA перевіряє те, що є: так перевіряються й останні мерджі перед тим, як робота зупиниться.

QA піднімає магазин зі свіжого `main` і проходить у браузері зміни кожного PR, а потім основні сценарії. Кожен знайдений баг стає issue з мітками `bug`, `qa`, пріоритетом і складністю й одразу потрапляє в чергу, а пріоритет вирішує, коли до нього дійде черга: `P3` — останнім. Підсумок прогону — issue `qa-report`, яке конвеєр закриває, щойно QA закінчить. Якщо звіту немає (QA обірвав ліміт чи перезапуск) або QA не зміг запустити магазин (звіт «QA не виконано: …»), ці PR перевіряються ще раз, але не більше одного разу. Якщо й удруге магазин не запустився, конвеєр надсилає сповіщення, а ці PR лишаються неперевіреними.

Перший прогін почнеться з найстаріших змерджених PR, які змінили код магазину.

## Docker

Кодери й QA запускають магазин, а його база — сервіс `db` з `docker-compose.yml`. Агенти Docker самі не запускають (AGENTS.md), тож перед тим, як найняти кодера чи QA, конвеєр виконує `docker compose up --detach --wait db`. Якщо Docker не працює (наприклад, після перезавантаження Mac), конвеєр один раз відкриває Docker Desktop (`docker.app`) і перевіряє знову на наступному кроці. Поки бази немає, кодерів і QA він не наймає, а рев'ю й мерджі тривають. Якщо Docker так і не запрацював за `docker.waitMinutes` хвилин або сама база не піднімається, конвеєр один раз надсилає сповіщення. Якщо порт бази вже зайнятий іншим контейнером чи PostgreSQL, конвеєр вважає, що база є.

У `docker-compose.yml` задано ім'я проєкту (`name: shop-edelweiss`), тож з будь-якого worktree `docker compose` працює з тим самим контейнером бази, а кожен агент має в ньому власну базу даних.

## Сповіщення

Конвеєр показує сповіщення macOS, коли щось отримує `needs-human`, коли агент упирається в ліміт, коли не вдається запустити Docker і коли QA закінчує. Їх показує `osascript` від імені Script Editor, тож якщо сповіщень не видно, увімкни їх для Script Editor у System Settings → Notifications.

## Мітки

| Мітка | Хто ставить | Що означає |
|---|---|---|
| `agent` | ти | Задача в черзі, навіть без пріоритету |
| `manual` | ти | Задача не для агентів |
| `hard` / `medium` / `easy` | ти, QA | Складність: хто з кодерів бере задачу |
| `P0-critical` … `P3-low` | ти, агенти | Пріоритет. Твої issues з ним потрапляють у чергу самі |
| `review:approved` / `review:changes` | конвеєр | Вердикт останнього рев'ю |
| `needs-human` | конвеєр | Конвеєр зупинився, потрібне твоє рішення |
| `merge-ok` | ти | Схвалений PR, який конвеєр сам не мерджить, можна мерджити: він підтягне main і змерджить, щойно CI позеленіє. Конфлікт чи червоний CI після мітки конвеєр виправляє сам і мерджить, коли рев'ю схвалить нові коміти |
| `qa` | QA | Баг, який знайшов QA |
| `qa-report` | QA | Звіт QA-прогону |

## Запуск

1. Запусти офіс: `agent-office /Users/pavlo/Documents/pet/shop-edelweiss`. У вікні черги постав **Workers at once = 0**, щоб агентів наймав лише конвеєр.
2. В офісі підійди до вільного столу й натисни **B**: відкриється 🐚-термінал. Клавіша **L** повісить над столом табличку, наприклад «Конвеєр».
3. Спершу перевір, що конвеєр зробив би, нічого не змінюючи:
   ```bash
   node tools/conveyor/conveyor.mjs --dry-run
   ```
4. Якщо все виглядає правильно, запускай по-справжньому:
   ```bash
   node tools/conveyor/conveyor.mjs
   ```
   Зупинити — **Ctrl+C**. Стан зберігається в `state.json`, тож після перезапуску конвеєр продовжить з того самого місця.

Поза офісом конвеєр працює тільки з `--dry-run`, бо наймати агентів можна лише з офісу. Параметр `--once` робить один крок і завершує роботу.

## Налаштування (`config.json`)

| Параметр | Що це |
|---|---|
| `intervalSeconds` | Як часто робити крок |
| `issueLabel` | Мітка, яка ставить issue в чергу |
| `manualLabel` | Мітка, яка не пускає issue в чергу |
| `autoPriorities` | З якими пріоритетами твої issues потрапляють у чергу без мітки `issueLabel` |
| `difficultyLabels`, `defaultDifficulty` | Мітки складності і складність issue без мітки |
| `coders.<ім'я>` | Кодер: агент, модель, effort, які складності бере (`takes`) і на яких портах та з якою базою працює (`ports`) |
| `maxOpenPullRequests` | Скільки PR може бути в роботі одночасно, поки конвеєр не бере нових задач |
| `maxReviewRounds` | Після скількох рев'ю з вердиктом `changes` здатися (`needs-human`) |
| `escalateTo` | Кодер, який робить останнє доопрацювання замість автора PR |
| `maxFixRounds` | Скільки всього доопрацювань може бути в одного PR |
| `maxIssueAttempts` | Скільки разів пробувати задачу, якщо агент не відкрив PR |
| `needsInputMinutes` | Скільки агент може чекати на відповідь у терміналі, перш ніж це стане `needs-human` |
| `limitPauseMinutes` | На скільки хвилин ставити паузу, коли в провайдера закінчився ліміт підписки, а час скидання з повідомлення невідомий |
| `releaseAfterHours` | Окремо для кожного провайдера: якщо ліміт скидається пізніше, ніж за стільки годин, агент іде додому, а його задача повертається в чергу |
| `modelDownHours` | На скільки годин ставити на паузу модель, яка недоступна чи зникла зі списку OpenCode, перш ніж спробувати її знову |
| `reviewer` | Агент, модель і effort рев'юера |
| `reviewerFor.<складність>` | Інший рев'юер для PR задач цієї складності (зараз Sonnet для `easy`) |
| `qa.enabled`, `qa.everyMerges` | Чи запускати QA і після скількох мерджів коду |
| `qa.maxWaitHours` | Скільки годин найстаріший неперевірений мердж може чекати, поки набереться `qa.everyMerges`; потім QA перевіряє те, що є |
| `qa.provider`, `qa.model`, `qa.effort` | Агент, модель і effort для QA |
| `qa.maxIssues` | Скільки нових issues QA може завести за один прогін |
| `qa.paths` | Зміни в яких папках рахуються мерджами коду |
| `qa.ports` | Порти й база, на яких QA запускає магазин |
| `docker.enabled` | Чи перевіряти базу перед тим, як найняти кодера чи QA |
| `docker.app`, `docker.service` | Яку програму відкривати, коли Docker не працює, і який сервіс `docker compose` піднімати |
| `docker.waitMinutes` | Скільки хвилин чекати, поки Docker запуститься, перш ніж надіслати сповіщення |
| `notify.enabled` | Чи показувати сповіщення macOS |
| `merge.enabled` | Чи мерджити самостійно (`false`: конвеєр лише ставить `review:approved`) |
| `merge.maxChangedLines` | Більші PR мерджить лише людина. Lock-файли (`package-lock.json` тощо) і тести не рахуються |
| `merge.okLabel` | Мітка, якою людина дозволяє змерджити схвалений PR, що зупинився через розмір чи захищені файли |
| `merge.doubleReview` | Захищені шляхи (`paths`), невеликий PR у яких (до `maxChangedLines` рядків без тестів) мерджать два схвалення Opus замість людини |
| `merge.protectedPaths` | PR, які чіпають ці файли, мерджить лише людина |

Промпти ролей лежать у `prompts/`: `coder.md`, `fix.md`, `review.md`, `qa.md`.

## Перевірка змін у конвеєрі

```bash
node tools/conveyor/test/run.mjs
```

Сценарії проганяють по одному кроку копії конвеєра в тимчасовій папці, з фейковими `gh`, `office-workers`, `osascript`, `docker` і `open`. Кожен сценарій перевіряє, що конвеєр зробив, а чого не робив. GitHub, офіс і справжній `state.json` при цьому не зачіпаються. Змінюєш поведінку конвеєра — додай сценарій.

## Безпека

- Конвеєр бере лише PR зі свого акаунта і не з форків. Вердикти рев'ю рахуються тільки з коментарів свого акаунта, бо коментувати публічний репозиторій може будь-хто.
- Мерджить лише після вердикту `approve` для поточного коміту, із зеленим CI і без конфлікту. Захист гілки `main` на GitHub (обов'язковий CI) — додаткова страховка.
- Агенти працюють за правилами з `AGENTS.md` і дозволами з `.claude/settings.json` (Claude), `.codex/config.toml` (Codex) та `opencode.json` (OpenCode). Змінювати сам конвеєр і ці файли агентам заборонено, і такі PR мерджить лише людина.
- Текст issue потрапляє агентам як задача. Тому мітку `agent` став лише на ті issues, яким довіряєш. Без цієї мітки, лише за пріоритетом, конвеєр бере тільки issues з твого акаунта: відкрити issue в публічному репозиторії може будь-хто.

`state.json` і `conveyor.log` не потрапляють у git.
