# Конвеєр

Скрипт-диспетчер, який без участі людини веде задачі через Agent Office: issue → код → CI → рев'ю → мердж → QA. Сам він не витрачає токенів моделей: лише читає GitHub і стан офісу, а потім наймає агентів і мерджить.

## Як рухається задача

```
issue у черзі ──► кодер (завжди один) ──► PR
PR відстає від main або CI ще не запускався ──► підтягнути main у гілку ──► CI
конфлікт або червоний CI ──► повернути автору (або найняти фіксера)
CI зелений, вердикту нема ──► рев'юер (по одному PR за раз) ──► коментар із вердиктом
вердикт changes ──► повернути на доопрацювання ──► рев'ю знову (максимум maxReviewRounds кіл)
вердикт approve ──► мердж, якщо PR не чіпає захищені файли й не завеликий
кожні qa.everyMerges мерджів коду ──► QA-агент у браузері ──► issues з багами і звіт
```

У черзі — відкриті issues з міткою `agent`, а також твої issues з пріоритетом `P0`–`P2` (`autoPriorities`). Мітка `manual` не пускає issue в чергу. Першим іде вищий пріоритет, а за однакового — старіше issue.

Усе, що конвеєр не може зрушити сам, отримує мітку `needs-human` і коментар із причиною. Коли знімаєш мітку, задача повертається в конвеєр, а лічильники кіл і спроб для неї починаються з нуля.

Коли в агента закінчується ліміт підписки, конвеєр помічає це в терміналі агента, на `limitPauseMinutes` нікого нового не наймає, а потім будить того ж агента продовжити задачу.

## QA

Коли після останнього QA змерджено `qa.everyMerges` PR, які змінили код магазину (`qa.paths`), конвеєр наймає QA-агента. QA займає слот кодера, бо обидва запускають магазин на тих самих портах. Поки QA чекає на вільний слот, нові задачі не починаються.

QA піднімає магазин зі свіжого `main` і проходить у браузері зміни кожного PR, а потім основні сценарії. Кожен знайдений баг стає issue з мітками `bug`, `qa` і пріоритетом: з `P0`–`P2` воно одразу потрапляє в чергу, а з `P3` чекає на тебе. Підсумок прогону — issue `qa-report`, яке конвеєр закриває, щойно QA закінчить.

Під час першого запуску QA перевіряє останні змерджені PR, тож може стартувати одразу.

## Сповіщення

Конвеєр показує сповіщення macOS, коли щось отримує `needs-human`, коли агент упирається в ліміт і коли QA закінчує. Їх показує `osascript` від імені Script Editor, тож якщо сповіщень не видно, увімкни їх для Script Editor у System Settings → Notifications.

## Мітки

| Мітка | Хто ставить | Що означає |
|---|---|---|
| `agent` | ти | Задача в черзі, навіть без пріоритету чи з `P3` |
| `manual` | ти | Задача не для агентів |
| `P0-critical` … `P3-low` | ти, агенти | Пріоритет. Твої issues з `P0`–`P2` потрапляють у чергу самі |
| `review:approved` / `review:changes` | конвеєр | Вердикт останнього рев'ю |
| `needs-human` | конвеєр | Конвеєр зупинився, потрібне твоє рішення |
| `qa` | QA | Баг, який знайшов QA |
| `qa-report` | QA | Звіт QA-прогону |

## Запуск

1. Запусти офіс: `agent-office /Users/pavlo/Documents/pet/shop-edelweiss`. У вікні черги постав **Workers at once = 0**, щоб агентів наймав лише конвеєр.
2. В офісі підійди до вільного столу й натисни **B**: відкриється 🐚-термінал. Клавіша **L** повісить над столом табличку, наприклад «Конвеєр».
3. Спершу перевір, що конвеєр зробив би, нічого не змінюючи:
   ```bash
   node tools/conveyor/conveyor.mjs --dry-run
   ```
4. Якщо все виглядає правильно, запускай по-справжньому:
   ```bash
   node tools/conveyor/conveyor.mjs
   ```
   Зупинити — **Ctrl+C**. Стан зберігається в `state.json`, тож після перезапуску конвеєр продовжить з того самого місця.

Поза офісом конвеєр працює тільки з `--dry-run`, бо наймати агентів можна лише з офісу. Параметр `--once` робить один крок і завершує роботу.

## Налаштування (`config.json`)

| Параметр | Що це |
|---|---|
| `intervalSeconds` | Як часто робити крок |
| `issueLabel` | Мітка, яка ставить issue в чергу |
| `manualLabel` | Мітка, яка не пускає issue в чергу |
| `autoPriorities` | З якими пріоритетами твої issues потрапляють у чергу без мітки `issueLabel` |
| `maxOpenPullRequests` | Скільки PR може бути в роботі одночасно, поки конвеєр не бере нових задач |
| `maxReviewRounds` | Після скількох рев'ю з вердиктом `changes` здатися (`needs-human`) |
| `maxFixRounds` | Скільки всього доопрацювань може бути в одного PR |
| `maxIssueAttempts` | Скільки разів пробувати задачу, якщо агент не відкрив PR |
| `needsInputMinutes` | Скільки агент може чекати на відповідь у терміналі, перш ніж це стане `needs-human` |
| `limitPauseMinutes` | На скільки ставити паузу, коли закінчився ліміт підписки |
| `coder`, `reviewer` | Агент, модель і effort для кожної ролі |
| `qa.enabled`, `qa.everyMerges` | Чи запускати QA і після скількох мерджів коду |
| `qa.provider`, `qa.model`, `qa.effort` | Агент, модель і effort для QA |
| `qa.maxIssues` | Скільки нових issues QA може завести за один прогін |
| `qa.paths` | Зміни в яких папках рахуються мерджами коду |
| `notify.enabled` | Чи показувати сповіщення macOS |
| `merge.enabled` | Чи мерджити самостійно (`false`: конвеєр лише ставить `review:approved`) |
| `merge.maxChangedLines` | Більші PR мерджить лише людина |
| `merge.protectedPaths` | PR, які чіпають ці файли, мерджить лише людина |

Промпти ролей лежать у `prompts/`: `coder.md`, `fix.md`, `review.md`, `qa.md`.

## Безпека

- Конвеєр бере лише PR зі свого акаунта і не з форків. Вердикти рев'ю рахуються тільки з коментарів свого акаунта, бо коментувати публічний репозиторій може будь-хто.
- Мерджить лише після вердикту `approve` для поточного коміту, із зеленим CI і без конфлікту. Захист гілки `main` на GitHub (обов'язковий CI) — додаткова страховка.
- Агенти працюють за правилами з `AGENTS.md` і дозволами з `.claude/settings.json`. Змінювати сам конвеєр і ці файли агентам заборонено, і такі PR мерджить лише людина.
- Текст issue потрапляє агентам як задача. Тому мітку `agent` став лише на ті issues, яким довіряєш. Без цієї мітки, лише за пріоритетом, конвеєр бере тільки issues з твого акаунта: відкрити issue в публічному репозиторії може будь-хто.

`state.json` і `conveyor.log` не потрапляють у git.
